# High-Density Investigation Workbench for Developer Mode

*   **Author:** Charan Sri Teja
*   **Status:** Proposed
*   **Date:** 2026-11-09

--------------------------------------------------------------------------------

## Overview

HarnessLab is an automated optimization harness for DataOps AI agents answering business questions against synthetic PostgreSQL databases. During benchmark evaluation and candidate screening, engineers must rapidly inspect what the agent is executing and diagnose why an investigation succeeded, hallucinated, or failed.

Currently, the developer mode (`technical` view in `apps/web`) toggles label text within the business layout. It splits run evidence across two disconnected tabs: an aggregate "Live Output & Data" tab and a raw "Technical Trace & Graph" tab where tool arguments are buried in collapsed `<details>` blocks.

This feature introduces a high-density **Investigation Workbench** in `apps/web/src/workbench.tsx` and mounts it directly inside `apps/web/src/trace.tsx` for developer mode. It unifies the investigation sequence: bypassing the disconnected tab layout entirely in technical mode, elevating SQL executions as first-class visual inspection units displaying the query, active harness parameters, latency delta, and tabular result sets, while condensing non-query events into 28px expandable log pills with automated exception elevation for errors and policy denials.

--------------------------------------------------------------------------------

## The Problem

When developing and tuning agent configurations (such as schema inspection policies, retry budgets, and prompt guidance), engineers need to answer three core questions for every task run:
1. *What configuration and task parameters guided the agent?* (Active harness guidance & knobs)
2. *What exact database query did it execute?* (SQL query & parameters)
3. *What data did PostgreSQL return, or why did it fail?* (Tabular rows, error code, execution duration)

Under the current implementation in `apps/web`:
* **Chronological Disconnect Between Reasoning and Queries**: The "Live Output & Data" tab (`LiveDataView`) extracts queries and results into static summary cards, detached from chronological sequence. An engineer cannot tell which query was generated by which turn.
* **Low Information Density**: The "Technical Trace & Graph" tab renders large Mantine cards with high whitespace and hides raw arguments and output inside `<details>` HTML dropdowns, requiring repeated manual expansion of collapsed elements.
* **Hidden Upstream Failures**: If an agent gets stuck looping on `describe_schema`, fails JSON validation, or gets blocked by an AST safety guardrail, there is no high-visibility callout. The engineer must manually hunt through collapsed event rows to find the error.
* **Disconnected Tab Overhead**: In developer mode, switching back and forth between "Live Output & Data" and "Technical Trace" breaks investigation continuity during rapid evaluation.

--------------------------------------------------------------------------------

## Goals

*   **Unified Chronological Workbench**: In developer mode (`viewMode === "technical"`), bypass the inner `<Tabs>` wrapper entirely in `apps/web/src/trace.tsx` and render a single, high-density investigation workbench.
*   **First-Class SQL Execution Cards**: Prominently display executed SQL queries in monospace syntax blocks, accompanied by active harness guidance, query execution latency (`tool_result.elapsed_ms - tool_request.elapsed_ms`), row counters, and tabular result data grids.
*   **Constrained Data Viewports**: Constrain tabular database output to a max height (260px) with sticky column headers and horizontal/vertical scroll handling to prevent runaway page height.
*   **Compact Non-Query Log Pills**: Condense non-SQL events (`start`, `model_usage`, `tool_request`, `tool_result`, `policy_decision`, `fault`, `recovery`, `grade`) into compact 28px log pills displaying sequence number, cumulative timeline offset, action name, target summary, and status dot.
*   **Automated Exception Elevation**: Any non-query event with an error (`status === "error"`), retry, or policy denial (`kind === "policy_decision" && (payload.safety_violation || outcome_code !== "success")`) automatically breaks the collapse rule and renders as an expanded alert banner.
*   **First-Class Terminal Answer & Clarification Rendering**: Render `final_output` events as dedicated outcome cards, displaying synthesized findings or clarification questions (`WorkerAnswer`) with citation links.
*   **Unified Dual-Arm Tournament Controls**: In comparison view (`apps/web/src/comparison.tsx`), lift workbench filter controls to the parent container so a single toolbar filters both arms simultaneously.
*   **Causal Divergence Pinpointing**: In tournament comparisons, automatically identify the first execution step where the candidate arm diverged from the baseline and render a visual divergence badge.
*   **Ergonomic Controls & Hotkeys**: Provide quick filter toggles (*"SQL Only"*, *"Expand All Logs"*, and *"Collapse All Logs"*) alongside keyboard shortcuts (`s` for SQL Only, `j`/`k` for query navigation, `c` to copy query).
*   **Zero Regression for Business View**: Preserve the existing executive presentation and metric cards unchanged when `viewMode === "business"`.

--------------------------------------------------------------------------------

## Non-Goals

*   **Modifying Business View**: No changes to the layout, cards, or styling of `viewMode === "business"`.
*   **Backend or Schema Modifications**: No changes to Fastify API routes, BullMQ jobs, database migrations, or `@harnesslab/schemas` type contracts (presentation layer only).
*   **In-Browser Ad-Hoc Execution**: No interactive SQL query editor or write-access terminal connected to synthetic sandboxes.
*   **Replacing the LangGraph Viewer**: The LangGraph graph component remains available as an optional collapsible inspection companion.
*   **Cross-Session LocalStorage Persistence**: Log pill expansion state is session-ephemeral and resets per task run navigation to avoid stale state bugs.

## Critical User Journeys (CUJs)

### CUJ 1: Diagnosing a Query Syntax or Schema Failure

*   **Given**: An agent run where the model generated a SQL query referencing a nonexistent column or table.
*   **When**: An engineer opens the task run in Developer Mode (`viewMode === "technical"`).
*   **Then**: The workbench immediately highlights the failed SQL execution card with a red error badge, displaying the error code alongside the SQL query and cumulative offset, while any preceding `describe_schema` or `fault` log pill is automatically elevated with warning styling.

### CUJ 2: Comparing Multi-Turn SQL Strategies Across Arms

*   **Given**: An A/B tournament comparison where the candidate arm succeeded with fewer tokens and lower latency than the baseline.
*   **When**: The engineer activates the "SQL Only" filter toggle in the shared comparison toolbar.
*   **Then**: All intermediate non-query log pills are hidden across both arms, displaying only the executed SQL queries, delta latencies, and tabular outputs, with the divergence point anchored by a `[⚡ Divergence Point]` badge.

### CUJ 3: Inspecting Upstream Guardrail Interceptions

*   **Given**: An agent turn where the model attempted an unauthorized write operation or violated AST allowlist constraints.
*   **When**: The engineer opens the trace view.
*   **Then**: The `policy_decision` event automatically elevates out of its collapsed state into an expanded red alert banner displaying `reason` (e.g. `disallowed_statement_type`) and `safety_violation: true`.

### CUJ 4: Inspecting Underspecified Requests & Clarifications

*   **Given**: A task run on an underspecified benchmark request where the agent correctly generated a clarification question instead of executing a blind SQL query.
*   **When**: The engineer opens the task run in Developer Mode.
*   **Then**: The workbench renders the `final_output` card prominently at the top, displaying the clarification question, missing fields, and preceding discovery pills.

## Technical Plan (Architecture)

### 1. High-Level Architecture & Cohesive Component Map

The technical investigation workbench resides entirely within the frontend presentation layer in `apps/web`. Following the established pattern of cohesive domain modules (`comparison.tsx`, `live-data.tsx`, `graph.tsx`), all workbench logic is consolidated into `apps/web/src/workbench.tsx`, with shared stream extraction housed in `apps/web/src/live-data.tsx`.

```text
apps/web/src/
├── trace.tsx                  # Conditional root: renders InvestigationWorkbench when technical, Tabs when business
├── live-data.tsx              # Extends extractLiveData with extractInvestigationSteps() reusing SqlExecution
├── workbench.tsx              # Consolidated domain module:
│   ├── InvestigationWorkbench # Root container with keyboard shortcuts & state
│   ├── SqlExecutionCard       # SQL Editor + Latency Delta + Tabular Data Grid
│   ├── CollapsedLogPill       # 28px expandable pill with auto-elevation & JSON drawer
│   ├── FinalOutputCard        # Clarification & answer rendering
│   └── WorkbenchControls      # Shared toolbar (SQL Only, Expand/Collapse, Divergence Badge)
└── comparison.tsx             # Embeds shared WorkbenchControls above dual-arm .pair-grid
```

### 2. Event Stream Extraction & Discrimination Pipeline

In `apps/web/src/live-data.tsx`, `extractLiveData()` is augmented to export a pure function `extractInvestigationSteps(items: TraceEvent[])`:

1. **Step Discrimination**:
   * **SQL Execution Step (`SqlQueryStep`)**: Formed when a `tool_request` for `execute_readonly_sql` pairs with its corresponding `tool_result`:
     - `seq`: Tool request sequence number.
     - `sql`: Raw SQL query string.
     - `status`: `"ok" | "error" | "timeout"`.
     - `cumulative_ms`: Cumulative timeline offset (`item.elapsed_ms`).
     - `duration_ms`: Execution duration delta (`tool_result.elapsed_ms - tool_request.elapsed_ms`).
     - `columns`: Metadata `Array<{ name: string; type: string }>`.
     - `rows`: Tabular data rows `Scalar[][]`.
     - `error`: Error code or message if execution failed.
   * **Final Output Step (`FinalOutputStep`)**: Formed when `kind === "final_output"`:
     - `seq`: Sequence number.
     - `answer`: Typed `WorkerAnswer` payload (findings, clarification question, or unable reason).
     - `cumulative_ms`: Timeline offset.
   * **Non-Query Log Step (`NonQueryLogStep`)**: Formed for all other lifecycle and tool events (`start`, `model_usage`, non-SQL `tool_request`/`tool_result`, `policy_decision`, `fault`, `recovery`, `grade`):
     - `seq`: Sequence number.
     - `kind`: Event kind.
     - `actionName`: Tool name or lifecycle event label.
     - `summary`: Compact single-line summary extracted from arguments or payload.
     - `status`: `"ok" | "warning" | "error" | "denied"`.
     - `cumulative_ms`: Timeline offset.
     - `rawPayload`: Full JSON payload for on-demand expansion.
     - `autoElevate`: `true` if `status === "error" || item.payload.safety_violation || (item.outcome_code && item.outcome_code !== "success")`.

### 3. Data Flow Diagram

```mermaid
flowchart TD
    API["Fastify API: /runs/:id/trace"] -->|Fetch TraceEvent[]| LT["loadTrace() in trace.tsx"]
    LT --> Mode{"useViewMode()"}
    
    Mode -->|"business"| BV["Mantine <Tabs>\n- Live Output & Data (LiveDataView)\n- Technical Trace & Graph"]
    Mode -->|"technical"| WB["InvestigationWorkbench (Direct Mount)"]
    
    WB --> Extract["live-data.tsx:\nextractInvestigationSteps()"]
    Extract --> Steps["ExecutionStep[] Stream"]
    
    Steps --> Filter{"WorkbenchControls Filter\n(All vs SQL Only)"}
    
    Filter -->|"execute_readonly_sql"| SQL["SqlExecutionCard\n- Monospace SQL Editor\n- Latency Delta & Offset\n- 260px Tabular Data Grid"]
    Filter -->|"final_output"| ANS["FinalOutputCard\n- Business Answer / Clarification"]
    Filter -->|"non-query events"| NonSQL{"Auto-Elevate Check\n(Error, Warning, or Denied?)"}
    
    NonSQL -->|"Normal"| Pill["CollapsedLogPill (28px)\nClick to expand JSON drawer"]
    NonSQL -->|"Failure/Denied"| Alert["Elevated Alert Banner\nDisplays reason & safety_violation"]
```

### 4. Component Design Specifications

#### A. `SqlExecutionCard`
* **Card Frame**: Bordered Mantine `Card` with high contrast.
* **Top Header**:
  - Ordinal badge: `Query #N of Total`.
  - Latency: `Duration: X ms · +Y ms offset`.
  - Row counter: `N rows returned`.
  - Outcome pill: Green `200 OK`, Red `SYNTAX_ERROR`, or Yellow `TIMEOUT`.
* **SQL Query Block**:
  - Monospace code block styled as an editor pane with one-click "Copy SQL" button.
* **Tabular Data Grid**:
  - Rendered using Mantine `<Table striped highlightOnHover withTableBorder>`.
  - Constrained to `max-height: 260px` with `overflow: auto` and `position: sticky` headers.
  - Formats `NULL` values distinctively with muted badges to prevent misinterpreting empty cells.

#### B. `CollapsedLogPill`
* **Dimensions**: Fixed 28px height in default collapsed state.
* **Typography & Content**:
  - Monospace sequence tag `[#02]`.
  - Cumulative offset `+180ms`.
  - Category icon (`📋` schema, `⚡` model, `🔢` math, `🛡️` policy, `⚠️` fault).
  - Truncated argument summary (e.g. `tables: ["customers", "orders"]`).
  - Right-aligned status indicator pill.
* **Interaction**: Clicking toggles an inline accordion drawer revealing the formatted JSON payload with syntax styling.
* **Auto-Elevation**: If `autoElevate === true`, the component defaults to open with an amber/red border and warning icon.

#### C. `WorkbenchControls` & Tournament Dual-Arm Behavior
* **Comparison Integration**: In `apps/web/src/comparison.tsx`, `WorkbenchControls` is rendered once above the side-by-side `.pair-grid` container. Toggling "SQL Only" or "Expand All" applies across both arms simultaneously.
* **Causal Divergence Pinpointing**: In tournament view, the controller computes the first step index where Arm 01 and Arm 02 deviate (by tool name, SQL query string, or outcome code), badging that step on both arms with `[⚡ Divergence Point: Step #N]`.
* **Keyboard Hotkeys**:
  - `s`: Toggle SQL Only filter.
  - `j` / `k`: Scroll to next / previous SQL execution card.
  - `c`: Copy SQL query of the currently focused card.

#### D. State Management & Reset Semantics
* `expandedPills: Map<number, boolean>`: Initialized on mount with `autoElevate` values (`true` for errors/denials, `false` for normal pills).
* *"Expand All Logs"*: Sets all entries in `expandedPills` to `true`.
* *"Collapse All Logs"*: Resets user-toggled entries to `false` while preserving `autoElevate === true`.
* Individual pill clicks toggle the entry in `expandedPills`.

## Alternatives Considered

### Alternative 1: Raw Terminal / JSON Stream

*   **Description**: Replace the event view with a monospaced terminal emulator (e.g. xterm.js or a virtualized raw JSON stream) that prints JSON log lines as they arrived.
*   **Pros**:
    *   Minimal frontend abstractions; directly mirrors raw backend event envelopes.
    *   Trivial implementation with low component maintenance.
*   **Cons**:
    *   Destroys structured tabular database representations.
    *   Forces developers to manually parse nested JSON strings and correlation IDs to decipher SQL inputs and outputs.
    *   High cognitive fatigue during rapid benchmark triage.
*   **Rejection Rationale**: *Terminal feeds destroy tabular representations, force manual parsing of raw JSON strings, and obscure structured query comparisons.*

### Alternative 2: Maintaining Disconnected Tabs ("Live Output" vs "Technical Trace")

*   **Description**: Keep the existing dual-tab setup in `apps/web/src/trace.tsx` (`📊 Live Output & Data` and `⚙️ Technical Trace & Graph`), but restyle each tab independently with higher contrast.
*   **Pros**:
    *   Requires minimal restructuring of existing component boundaries.
    *   Zero disruption to the existing tab navigation model.
*   **Cons**:
    *   Preserves the chronological disconnect: an engineer viewing extracted queries in the Live Data tab cannot see the preceding tool call or following policy event without switching tabs.
    *   Redundant rendering logic and duplicated event parsing.
*   **Rejection Rationale**: *Retaining separate tabs perpetuates the chronological disconnect between queries and lifecycle events, requiring constant context switching during investigation.*

### Alternative 3: Unconditional / Static Collapse of All Non-Query Events

*   **Description**: Collapse every non-SQL event into a static 28px pill, requiring the user to manually click any pill to inspect its status or contents.
*   **Pros**:
    *   Enforces an ultra-compact visual rhythm with zero exceptions.
    *   Simpler UI state management without automated expansion triggers.
*   **Cons**:
    *   Conceals critical upstream failure modes: an agent stuck in a schema loop or blocked by an AST safety guardrail appears as normal green pills unless manually clicked.
    *   Slows down failure diagnosis by requiring manual probing of every non-query turn.
*   **Rejection Rationale**: *Unconditional collapse hides critical upstream schema discovery loops, JSON validation failures, and security policy denials.*

### Alternative 4: Full-Screen Modal Inspector for Database Rows

*   **Description**: Render SQL cards with query text only, opening a full-screen modal or drawer to view returned rows and columns.
*   **Pros**:
    *   Allows displaying very wide tables (20+ columns) without horizontal scroll constraints within the card.
*   **Cons**:
    *   Breaks chronological reading flow by covering the trace timeline.
    *   Inhibits side-by-side visual comparison of Baseline versus Candidate query results in the dual-arm tournament view (`apps/web/src/comparison.tsx`).
*   **Rejection Rationale**: *Modal overlays disrupt chronological reading flow and prevent side-by-side visual comparison across tournament arms.*

## Risks & Mitigations

| Risk | Severity | Impact | Architectural Mitigation |
| :--- | :---: | :--- | :--- |
| **DOM Tree Bloat on Long Traces** | Medium | Traces with 50+ events and large tabular row sets could cause scrolling lag. | Constrain tabular viewports to `max-height: 260px` with sticky headers and cap initial table rendering to 100 rows with an overflow indicator. |
| **Dual-Arm Vertical Desynchronization** | Medium | Asymmetric step counts between Baseline and Candidate arms could cause comparison drift. | Lift `WorkbenchControls` to the parent container in `comparison.tsx` and provide synchronized scroll anchoring via `[⚡ Divergence Point]` jump targets. |
| **Schema Invariant Violation** | High | Reading non-existent fields (e.g. reasoning or query fingerprints) would break runtime or type checking. | Strictly bind to `@harnesslab/schemas/types` (`TraceEvent`, `WorkerAnswer`, `Scalar[][]`). Eliminate unbacked properties. |
| **State Desynchronization on Navigation** | Low | Persisting expanded pill states across different runs could cause stale accordion states. | Keep accordion and filter state local to the component instance; reset state cleanly on run ID changes. |

## Non-Functional Requirements

### 1. Security & Privacy
*   **Read-Only Integrity**: The workbench is purely a presentation layer. It does not introduce any interactive input fields capable of executing ad-hoc SQL or modifying database state.
*   **Redaction Preservation**: All strings rendered in the SQL block and log drawers are sourced from canonical `TraceEvent` payloads that have already undergone server-side redaction (per HarnessLab trust boundaries). No raw credentials or unredacted provider tokens are exposed.

### 2. Performance & Latency
*   **DOM Node Footprint**: By constraining tabular result viewports to `max-height: 260px` and capping initial table row renders to 100 rows, the workbench prevents layout recalculation lag.
*   **Pure Stream Parsing**: `extractInvestigationSteps` runs synchronously in memory with $O(N)$ linear complexity, adding negligible overhead (<2ms) on a 100-event trace.

### 3. Rollout & Backward Compatibility
*   **Zero Impact on Business View**: The workbench is strictly scoped to `viewMode === "technical"`. When `viewMode === "business"`, the existing executive scorecard and `LiveDataView` presentation remain unchanged.
*   **Graceful Degradation**: If a trace contains zero SQL queries, the workbench renders the `FinalOutputCard` or failure alert cleanly without layout collapse.

## Detailed Implementation Plan

### Target Files to Create/Modify

#### 1. `apps/web/src/live-data.tsx` (Modify)
*   **Type / Scope**: Pure Utility & Presentation Module
*   **Proposed Changes**:
    *   Export shared step models:
        ```typescript
        export interface SqlQueryStep {
          kind: "sql_query";
          seq: number;
          sql: string;
          status: "ok" | "error" | "timeout";
          cumulative_ms: number;
          duration_ms: number;
          columns?: { name: string; type: string }[];
          rows?: Scalar[][];
          error?: string;
        }

        export interface FinalOutputStep {
          kind: "final_output";
          seq: number;
          answer: WorkerAnswer;
          cumulative_ms: number;
        }

        export interface NonQueryLogStep {
          kind: "non_query_log";
          seq: number;
          eventKind: TraceEvent["kind"];
          actionName: string;
          summary: string;
          status: "ok" | "warning" | "error" | "denied";
          cumulative_ms: number;
          rawPayload: unknown;
          autoElevate: boolean;
        }

        export type ExecutionStep = SqlQueryStep | FinalOutputStep | NonQueryLogStep;
        ```
    *   Export pure function `extractInvestigationSteps(items: TraceEvent[]): ExecutionStep[]`:
        - Reuses `SqlExecution` pairing logic already in `live-data.tsx`.
        - Calculates `duration_ms` as `tool_result.elapsed_ms - tool_request.elapsed_ms`.
        - Maps `final_output` into `FinalOutputStep`.
        - Maps all other events to `NonQueryLogStep` with `autoElevate` set to true for errors, warnings, or `payload.safety_violation`.
