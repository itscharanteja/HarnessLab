# HarnessLab development handoff

## Current state

HarnessLab is a self-improving DataOps agent with human-gated updates. The Worker Graph investigates synthetic PostgreSQL data through read-only MCP tools. The Optimizer Graph uses sanitized development failures to suggest bounded YAML changes. The dispatcher evaluates candidates on matched tasks, and the operator reviews eligible results before activation.

- Phase 0–8 implementation is in Git through `1c2ae4c`. The dashboard replay follow-up was present as local working-tree changes when this handoff was written. Check `git status --short` before starting, preserve those changes, and use separate commits for provider contracts, adapters, and infrastructure.
- Local fixture CI and browser tests passed. Fixture mode uses scripted model responses and real SQL. The repository records no completed paid smoke test, hosted rollout, or signed-off private release validation and holdout bundles.
- Live OpenAI adapters exist for both graphs. Bedrock and AWS deployment are proposed work. The current deployment renderer targets Cloud Run and the hosted runbook assumes Vercel and Supabase. Preserve those paths while adding AWS.
- Read [AGENTS.md](AGENTS.md), [PLAN.md](PLAN.md), [the evidence log](docs/implementation-log.md), and [the operations runbook](docs/operations.md). Keep existing numbered phases and acceptance evidence. Add explicit follow-up milestones as the work lands.

## Start locally

Use the Node version in `.node-version`, Python in `.python-version`, Corepack, uv and Docker. From the repo root:

```sh
make bootstrap
make dev
make demo-fixture
make test-e2e
```

Open [the dashboard](http://localhost:3000). To understand the feedback loop, start a fixture, open a diagnosis failure, replay the baseline and candidate, and inspect the paired result and promotion gate. Use `make ci` as the full fixture regression gate. Keep CI credential-free.

## Milestone B — Add Bedrock Converse in the existing graphs

1. Select one exact Bedrock model or inference profile. Verify access in the intended AWS account and Region, its supported Converse parameters, structured output, context window, service tier, quotas, price, and geographic routing. Record these in an operator-controlled inventory. Avoid hardcoding an example model identifier into production defaults. [Converse guide](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference.html) · [Structured outputs](https://docs.aws.amazon.com/bedrock/latest/userguide/structured-output.html) · [Bedrock pricing](https://aws.amazon.com/bedrock/pricing/)
2. Pin Boto3 and its resolved dependencies in `uv.lock`, adding it to the Python packages and image targets that need it. Use the SDK default credential chain with an ECS task role in AWS and an authorized short-lived AWS profile for local smoke tests. Set the Region explicitly. Grant `bedrock:InvokeModel` on the approved resources. For cross-Region inference profiles verify required destination model permissions, Region restrictions and service control policies. Avoid static AWS keys. [Boto3 Converse reference](https://docs.aws.amazon.com/boto3/latest/reference/services/bedrock-runtime/client/converse.html)
3. Implement one non-streaming `bedrock-runtime.converse` request per worker turn or optimizer proposal call. Supply fixed instructions through `system` and delimited input through `messages`. Set the remaining output budget through `inferenceConfig.maxTokens`. Project `WorkerAction` and `ProposalBatch` into the selected model's supported JSON Schema subset and serialize the schema into `outputConfig.textFormat.structure.jsonSchema.schema`. Confirm model-specific required fields against its model card. Exercise first-use schema compilation separately under an approved budget because it can exceed a normal turn deadline. [Converse request shape](https://docs.aws.amazon.com/boto3/latest/reference/services/bedrock-runtime/client/converse.html) · [Structured output compilation](https://docs.aws.amazon.com/bedrock/latest/userguide/structured-output.html)
4. Keep Boto3's blocking network work off the async event loop. Use bounded concurrency, explicit connect/read deadlines, and Botocore `total_max_attempts=1`. Cancellation of an async wrapper does not cancel a request already in flight. Treat timeout or lost response after dispatch as an ambiguous paid effect under the existing lease, reservation and settlement rules.
5. Read the response stop reason, output content blocks, usage and SDK request ID. Enforce bounded JSON with duplicate-key rejection and validate again against the full local contract. Reject truncation, refusal, unexpected content such as provider tool calls, extra fields, or unsupported stop reasons. Preserve billable usage for malformed responses and fail closed on ambiguous or unsupported metering. Verify conservative input estimation for the selected model, including instructions, schema and protocol overhead. Keep both graph token limits and request ceilings in force.
6. Leave MCP invocation in the Worker Graph. Send no provider-hosted tools. The model returns one proposed action and the graph enforces tool scope, SQL safety, evidence, deadline and recovery. Keep reasoning, credentials and raw provider payloads out of stored traces. Verify Bedrock model invocation logging and retention settings against the deployment's data policy before paid traffic.
7. Keep the existing OpenAI adapter and fixture path. Add future providers at the same two boundaries with explicit capability validation, strict local contract checks, and their own usage normalization. Introduce shared helpers only where both roles actually share behavior.

### Provider acceptance

- Unit tests with fake clients or Botocore Stubber cover request shape, schema projection, timeout and no retry, valid action and proposal, wrong tool or malformed JSON, truncation and refusal, missing or inconsistent usage, and SDK error normalization.
- Contract tests prove legacy OpenAI manifests and envelopes replay with their original digests, Bedrock profiles pin the exact routing and price, and unsupported profile combinations are rejected before enqueue.
- Integration tests cover authenticated entry points, fixture parity, SQL dispatch and evidence, optimizer scope, checkpoint and redelivery behavior, and no second paid request after an ambiguous effect. Verify charging and reserve settlement for the chosen model's token categories. Keep provider credentials out of CI and public routes.
- Run `make contracts-check lint typecheck`, focused regression and integration tests, then `make ci`. Under explicit spend approval, smoke the worker on one signed-off development task, verify grading and usage, then smoke the optimizer with a sanitized development summary. Repeat separately for OpenAI and Bedrock. Adapt `scripts/live_checks.py` for AWS service identity before using its private endpoints there. The current worker smoke is documented in [the runbook](docs/operations.md#hosted-smoke-and-live-checks).

## Milestone C — Deploy a fixture-only AWS staging stack

Use Terraform or CDK under a new `infra/aws/` directory. Pick one tool and pin its versions. Add an AWS-specific validate/plan command and a restricted staging inventory for account, Region, VPC, subnets, service addresses, task roles, secret versions, immutable image digests and artifact checksums. Keep cloud writes out of ordinary CI and keep the existing Cloud Run renderer available.

| Component                       | Proposed AWS placement                                                                                                                                                                                                                |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Next.js web                     | ECS Fargate behind an HTTPS Application Load Balancer, ACM certificate and Route 53 record. Public traffic reaches only the web app. Its same-origin API proxy continues to use a server-side credential.                             |
| Fastify API and dispatcher      | Separate private ECS services. Start with one continuously running dispatcher and preserve the existing worker concurrency, PostgreSQL lease and spend controls. Configure readiness, graceful shutdown and alarms.                   |
| Runner, evaluator and optimizer | Private ECS services, one task role each. Use ECS Service Connect for private discovery and connectivity, with explicit allowed caller-to-service rules. The MCP subprocess stays inside the runner task.                             |
| Control DB and online sandbox   | Separate private RDS for PostgreSQL 16 instances. Preserve migrator, dispatcher, API, promoter, seeder and variant-reader grants. Use TLS with CA verification, backups and restore checks.                                           |
| BullMQ                          | Private node-based ElastiCache replication group with cluster mode disabled, TLS, backups, failover and a verified `noeviction` parameter. Assess the AOF decision below before production.                                           |
| Artifacts and secrets           | Private encrypted S3 buckets or tightly scoped prefixes for dispatcher prompts/faults, evaluator references, and trusted release profiles. Store service tokens, DSNs and any OpenAI keys in Secrets Manager.                         |
| Holdout                         | Separately authorized ECS task or AWS Batch job with an isolated sandbox, separate PostgreSQL ledger, restricted artifacts and private aggregate output. Give online identities neither access nor network routes to those resources. |

### Compatibility work before rollout

- **Private service identity.** The Cloud Run metadata token path and `X-Serverless-Authorization` are Google-specific. Implement and test the AWS caller matrix before switching that path off in the AWS environment. Use private ingress, security groups and separate application bearer tokens for each direction, including the runner and optimizer callback to the dispatcher. Preserve checkpoint capability and lease fence checks. If platform-level caller authentication is required, explicitly design and verify it. ECS task IAM and Service Connect discovery alone do not authenticate arbitrary HTTP callers.
- **Provider egress and IAM.** Give only the appropriate runner/optimizer roles and isolated holdout role Bedrock invoke permissions. Separate the ECS execution role for image pulls and injected secrets from the application task role. Use a Bedrock Runtime interface endpoint with private DNS where supported. Provide controlled egress for OpenAI and any external JWKS issuer if enabled. Scope S3, Secrets Manager and KMS access per service. Verify the MCP subprocess environment cannot inherit provider credentials or reach cloud metadata. Because it shares the runner task network, environment filtering alone cannot block network access to the ECS credential endpoint. Prove process-level isolation or move MCP to an equivalent separately isolated boundary before enabling a credentialed live runner.
- **Queue durability.** ElastiCache Redis OSS 7 does not offer the Compose AOF setting. If choosing ElastiCache, record the design change and prove that PostgreSQL outbox reconciliation restores work after failover, queue loss and restore. Test active leases, completed work, replay, duplicates and ambiguous paid effects under those failures. If AOF is mandatory, provision an approved Redis deployment that supports it and verify restore. [ElastiCache engine parameters](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/ParameterGroups.Engine.html)
- **Operator authentication.** Keep the existing Supabase issuer/JWKS integration for the first AWS deployment if available. For an AWS-native migration, add a separate Cognito verifier and verify issuer, signature, expiry, `token_use=access`, `client_id`, and API audience when resource-bound. Update the operator subject allowlist deliberately. Reject ID tokens and wrong issuer or client claims. Preserve anonymous session ownership and same-origin command checks. [Cognito JWT verification](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-using-tokens-verifying-a-jwt.html)
- **Artifact delivery.** Current services consume local file paths. Stage approved S3 objects into task-local storage before readiness, using separate scoped task roles or a trusted bootstrap. Verify signed-off digests, schema, scope, and mount paths. Keep oracle files out of dispatcher and runner tasks. Keep private bundles out of the image and Git. Adapt the holdout storage backend separately if moving its report publication to S3.

### Rollout order

1. Obtain staging account and Region approval. Review the IaC plan, estimated recurring costs, model access, quotas, IAM, network flows, retention and backups. Begin with `HL_MODE=fixture`, `HL_PUBLIC_RUNS=0` on API and dispatcher, no provider permissions or credentials, and separate staging data.
2. Provision VPC, subnets, security groups, endpoints, ECR, task roles, secrets and logs. Provision PostgreSQL and Redis. Apply control migrations using a one-off migrator task with its own role. Seed the synthetic sandbox separately and verify restrictions, hashes and TLS from the task network.
3. Build the pinned images from `infra/docker/node.Dockerfile` and `infra/docker/python.Dockerfile` with the targets and build args in Compose. Push each image to ECR from an authorized pipeline and pin task definitions by digest. Deploy the private Python services, dispatcher, API and web. Wire `HL_API_INTERNAL_URL`, `HL_PUBLIC_ORIGIN`, service URLs and scoped tokens from the staging inventory. Check health and readiness before routing HTTPS traffic.
4. Test proxy and direct ingress boundaries, operator auth denials, fixture quotas, restricted artifacts, and role permissions. Temporarily enable fixture submission during an approved window and run `make smoke-hosted BASE_URL=https://STAGING_HOST` and `HL_E2E_BASE_URL=https://STAGING_HOST make test-e2e`. Verify the dashboard, both trace projections, reports, and zero provider calls. Test dispatcher restart and Redis failover before advancing.
5. Configure the Bedrock task role, approved profile, matching price and live spend cap only after fixture staging passes. Deploy with operator-only live access. Run the bounded worker and optimizer checks from Milestone B, record actual usage, latency and model identity, and compare settlement to the reserved amount. Run an authorized full live trial only after installing signed-off private validation artifacts. Run the release holdout separately with explicit approval.
6. Monitor CloudWatch for queue age, lease expiry, provider throttling or timeouts, unknown usage, budget stops, and gate integrity failures. Set AWS Budgets alerts alongside the application's hard cap. For rollback, stop new admissions, drain or retain compatible workers for pinned work, redeploy the prior task definition digests, and verify readiness and queue recovery. Use the existing operator rollback path for the active harness pointer. Keep database backups and practice restores in staging.
