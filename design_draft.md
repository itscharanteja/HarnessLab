# High-Density Investigation Workbench for Developer Mode

*   **Author:** Charan Sri Teja
*   **Status:** Draft
*   **Date:** 2026-11-09

--------------------------------------------------------------------------------

## Overview

HarnessLab is an automated optimization harness for DataOps AI agents answering business questions against synthetic PostgreSQL databases. During benchmark evaluation and candidate screening, engineers must rapidly inspect what the agent is executing and diagnose why an investigation succeeded, hallucinated, or failed.

Currently, the developer mode (`technical` view in `apps/web`) acts as a cosmetic text swap over the business layout. It splits run evidence across two disconnected tabs: an aggregate "Live Output & Data" tab and a raw "Technical Trace & Graph" tab where tool arguments are buried in collapsed `<details>` blocks.

This feature introduces a high-density **Investigation Workbench** in `apps/web/src/trace.tsx` for developer mode. It unifies the causal investigation sequence: elevating SQL executions as first-class visual inspection units displaying the query, internal reasoning, and tabular result sets, while condensing non-query events into 28px expandable log pills with automated exception elevation for errors and policy denials.

--------------------------------------------------------------------------------

## The Problem

When developing and tuning agent configurations (such as schema inspection policies, retry budgets, and prompt guidance), engineers need to answer three core questions for every task run:
1. *What was the agent attempting to do?* (Internal reasoning & hypothesis)
2. *What exact database query did it execute?* (SQL query & parameters)
3. *What data did PostgreSQL return, or why did it fail?* (Tabular rows, error code, latency)

Under the current implementation in `apps/web`:
* **Severed Causal Chain**: The "Live Output & Data" tab (`LiveDataView`) extracts queries and results into static summary cards, completely divorced from chronological sequence. An engineer cannot tell which query was generated by which reasoning turn.
* **Low Information Density**: The "Technical Trace & Graph" tab renders large Mantine cards with high whitespace and hides raw arguments and output inside `<details>` HTML dropdowns, forcing dozens of manual clicks per investigation.
* **Hidden Upstream Failures**: If an agent gets stuck looping on `describe_schema`, fails JSON validation, or gets blocked by an AST safety guardrail, there is no high-visibility callout. The engineer must manually hunt through collapsed event rows to find the error.

--------------------------------------------------------------------------------

## Goals

*   **Unified Chronological Workbench**: Replace the disconnected "Live Data" versus raw trace tabs in developer mode (`viewMode === "technical"`) with a single, high-density investigation workbench.
*   **First-Class SQL Execution Cards**: Prominently display executed SQL queries in monospace syntax blocks, preceded by the agent's internal reasoning/hypothesis, and accompanied by tabular result data grids.
*   **Constrained Data Viewports**: Constrain tabular database output to a max height (260px) with sticky column headers and horizontal/vertical scroll handling to prevent runaway page height.
*   **Compact Non-Query Log Pills**: Condense non-SQL events (`start`, `model_usage`, `list_tables`, `describe_schema`, `get_business_definition`, `validate_calculation`, `policy_decision`) into compact 28px log pills displaying sequence number, elapsed time, action name, target summary, and status dot.
*   **Automated Exception Elevation**: Any non-query event with an error (`status === "error"`), retry, or policy denial (`kind === "policy_decision" && outcome_code !== "allowed"`) automatically breaks the collapse rule and renders as an expanded alert banner.
*   **Workbench Filter Controls**: Provide quick toggles at the top of the workbench: *"SQL Only"*, *"Expand All Logs"*, and *"Collapse All Logs"*.
*   **Zero Regression for Business View**: Preserve the existing executive presentation and metric cards entirely when `viewMode === "business"`.

--------------------------------------------------------------------------------

## Non-Goals

*   **Modifying Business View**: No changes to the layout, cards, or styling of `viewMode === "business"`.
*   **Backend or Schema Modifications**: No changes to Fastify API routes, BullMQ jobs, database migrations, or `@harnesslab/schemas` type contracts (presentation layer only).
*   **In-Browser Ad-Hoc Execution**: No interactive SQL query editor or write-access terminal connected to synthetic sandboxes.
*   **Replacing the LangGraph Viewer**: The LangGraph graph component remains fully intact and available as an inspection companion.

## Critical User Journeys (CUJs)

### CUJ 1: Diagnosing a Query Syntax or Schema Failure

*   **Given**: An agent run where the model generated a SQL query referencing a nonexistent column or table.
*   **When**: An engineer opens the task run in Developer Mode (`viewMode === "technical"`).
*   **Then**: The workbench immediately highlights the failed SQL execution card with a red error badge, displaying the error message alongside the SQL query and preceding reasoning, while any preceding `describe_schema` or `inspect_query_error` log pill is automatically expanded with warning highlights.

### CUJ 2: Comparing Multi-Turn SQL Strategies Across Arms

*   **Given**: An A/B tournament comparison where the candidate arm succeeded with fewer tokens and lower latency than the baseline.
*   **When**: The engineer activates the "SQL Only" filter toggle in the workbench.
*   **Then**: All intermediate non-query log pills are hidden, displaying only the executed SQL queries, reasoning, and tabular outputs across both arms for immediate visual diffing.

### CUJ 3: Inspecting Upstream Guardrail Interceptions

*   **Given**: An agent turn where the model attempted an unauthorized write operation or violated AST allowlist constraints.
*   **When**: The engineer opens the trace view.
*   **Then**: The `policy_decision` event automatically elevates out of its collapsed state into an expanded red alert banner detailing the exact policy denial reason and blocked query fingerprint.

## Technical Plan (Architecture)

### 1. High-Level Architecture & Component Map

The technical investigation workbench resides entirely within the frontend presentation layer in `apps/web`. It ingests the canonical `TraceEvent[]` stream returned by `loadTrace(id, token, signal)` and organizes it into a chronological sequence of typed execution steps.

```text
apps/web/src/
├── trace.tsx                          # Hosts InvestigationWorkbench when viewMode === "technical"
└── workbench/
    ├── types.ts                       # Clustered ExecutionStep models & filter state interfaces
    ├── parser.ts                      # Pure deterministic TraceEvent[] -> ExecutionStep[] clusterer
    ├── InvestigationWorkbench.tsx     # Main container with toolbar, virtual list, and sticky controls
    ├── SqlExecutionCard.tsx           # High-density card: Internal Reasoning + SQL Editor + Data Grid
    ├── CollapsedLogPill.tsx           # 28px expandable pill for non-query turns with auto-elevation
    └── WorkbenchControls.tsx          # "SQL Only", "Expand All Logs", "Collapse All Logs" toolbar
```

### 2. Event Stream Preprocessing & Clustering Pipeline

The existing `apps/web/src/live-data.tsx` implementation flattens and extracts query data out of order. The new parser (`apps/web/src/workbench/parser.ts`) processes the linear `TraceEvent[]` stream and forms coherent chronological clusters:

1. **Reasoning Turn Attribution**: When a `model_usage` event carries preceding agent reasoning text, the parser attaches it to the immediately following `tool_request`.
2. **Request-Result Pairing**: When a `tool_request` occurs, the parser matches it with its terminating `tool_result` by correlation ID or sequence pairing.
3. **Typing & Discrimination**:
   * If `tool_name === "execute_readonly_sql"`, emit a `SqlQueryStep`:
     - `seq`: Tool request sequence number.
     - `sql`: Raw SQL query string.
     - `reasoning`: Preceding thought or intent (if present).
     - `status`: `"ok" | "error" | "timeout"`.
     - `elapsed_ms`: Milliseconds taken.
     - `columns`: Column metadata `Array<{ name: string; type: string }>`.
     - `rows`: Tabular data rows `Scalar[][]`.
     - `error`: Error code or message if execution failed.
   * For all other actions (`describe_schema`, `list_tables`, `validate_calculation`, `policy_decision`, `start`), emit a `NonQueryLogStep`:
     - `seq`: Event sequence number.
     - `kind`: Event kind (`TraceEvent["kind"]`).
     - `action_name`: Tool or action label.
     - `summary`: One-line compact argument summary (e.g. `tables: ["orders"]`).
     - `status`: `"ok" | "warning" | "error" | "denied"`.
     - `raw_payload`: Full JSON payload for on-demand expansion.
     - `auto_elevate`: Boolean flag (`true` if status is error, retry, or policy denial).

### 3. Data Flow Diagram

```mermaid
flowchart TD
    API["Fastify API: /runs/:id/trace"] -->|Fetch TraceEvent[]| LT["loadTrace() in trace.tsx"]
    LT --> Mode{"useViewMode()"}
    
    Mode -->|"business"| BV["LiveDataView & Business Cards\n(Unchanged)"]
    Mode -->|"technical"| WB["InvestigationWorkbench"]
    
    WB --> Cluster["workbench/parser.ts\nclusterTraceEvents()"]
    Cluster --> Steps["ExecutionStep[] Stream"]
    
    Steps --> Filter{"WorkbenchControls Filter\n(All vs SQL Only)"}
    
    Filter -->|"execute_readonly_sql"| SQL["SqlExecutionCard\n- Internal Reasoning Block\n- Monospace SQL Block\n- 260px Tabular Data Grid"]
    Filter -->|"non-query events"| NonSQL{"Auto-Elevate Check\n(Error or Policy Denied?)"}
    
    NonSQL -->|"Normal"| Pill["CollapsedLogPill (28px)\nClick to expand raw JSON"]
    NonSQL -->|"Failure/Denied"| Alert["Expanded Alert Banner\nHigh-visibility triage warning"]
```

### 4. Component Design Specifications

#### A. `SqlExecutionCard.tsx`
* **Card Frame**: Bordered Mantine `Card` with subtle dark background (`var(--mantine-color-dark-7)` or `var(--mantine-color-gray-0)` depending on color scheme) and high contrast.
* **Top Header**:
  - Ordinal badge: `Query #N of Total`.
  - Latency: `+X ms`.
  - Row counter: `N rows returned`.
  - Outcome pill: Green `200 OK`, Red `SYNTAX_ERROR`, or Yellow `TIMEOUT`.
* **Internal Reasoning Section**:
  - Collapsible block rendered directly above the SQL query.
  - Formatted in clean muted italic typography, displaying the agent's intent prior to executing the query.
* **SQL Query Block**:
  - Monospace code block styled as an editor pane with one-click "Copy SQL" button.
* **Tabular Data Grid**:
  - Rendered using Mantine `<Table striped highlightOnHover withTableBorder>`.
  - Constrained to `max-height: 260px` with `overflow: auto` and `position: sticky` headers.
  - Formats `NULL` values distinctively with muted badges to prevent misinterpreting empty cells.

#### B. `CollapsedLogPill.tsx`
* **Dimensions**: Fixed 28px height in default collapsed state.
* **Typography & Content**:
  - Monospace sequence tag `[#02]`.
  - Elapsed timing offset `+180ms`.
  - Category icon (`📋` schema, `⚡` model, `🔢` math, `🛡️` policy).
  - Truncated argument summary (e.g. `tables: ["customers", "orders"]`).
  - Right-aligned status indicator pill.
* **Interaction**: Clicking toggles an inline accordion drawer revealing the formatted JSON payload with syntax styling.
* **Auto-Elevation**: If `auto_elevate === true`, the component defaults to open with an amber/red border and warning icon, eliminating the risk of hidden upstream failures.

#### C. `WorkbenchControls.tsx`
* **Toolbar Actions**:
  - `SQL Only` switch: Instantly filters the view to show only database queries.
  - `Expand All Logs` / `Collapse All Logs`: Global accordion control for all non-query pills.
  - Step counter badge: Displays total tool calls, total queries, and total errors.

### 5. Failure Modes & Edge Case Safeguards

1. **Zero SQL Executions**: In tasks where the request is ambiguous (agent emits a clarification question) or where the run fails during initial schema discovery, the workbench displays an empty state banner with the clarification or failure reason, ensuring the view remains functional.
2. **Large Result Sets**: Queries returning 100+ rows do not degrade DOM performance because of the max-height scroll viewport; optional row truncation warning appears if rows exceed 100.
3. **Policy Denials**: If `policy_decision` denies an operation (e.g. blocked AST mutation), the event is marked `auto_elevate: true` and rendered with a high-contrast danger badge.

## Alternatives Considered

### Alternative 1: Raw Terminal / JSON Stream

*   **Description**: Replace the event view with a monospaced terminal emulator (e.g. xterm.js or a virtualized raw JSON stream) that prints JSON log lines as they arrived.
*   **Pros**:
    *   Minimal frontend abstractions; directly mirrors raw backend event envelopes.
    *   Trivial implementation with low component maintenance.
*   **Cons**:
    *   Destroys structured tabular database representations.
    *   Forces developers to manually parse nested JSON strings and correlation IDs to decipher SQL inputs and outputs.
    *   High cognitive fatigue during rapid benchmark triage.
*   **Reason for Rejection**: *Rejected by author: Text-only terminal feeds force developers to parse nested JSON manually and destroy structured tabular database representations.*

### Alternative 2: Maintaining Disconnected Tabs ("Live Output" vs "Technical Trace")

*   **Description**: Keep the existing dual-tab setup in `apps/web/src/trace.tsx` (`📊 Live Output & Data` and `⚙️ Technical Trace & Graph`), but restyle each tab independently with higher contrast.
*   **Pros**:
    *   Requires minimal restructuring of existing component boundaries.
    *   Zero disruption to the existing tab navigation model.
*   **Cons**:
    *   Completely severs the causal investigation loop: an engineer viewing extracted queries in the Live Data tab cannot see the preceding thought or following policy event without switching tabs.
    *   Redundant rendering logic and duplicated event parsing.
*   **Reason for Rejection**: *Rejected by author: Separating high-level data from the event list breaks causal debugging and prevents seeing which reasoning step created which query.*

### Alternative 3: Unconditional / Static Collapse of All Non-Query Events

*   **Description**: Collapse every non-SQL event into a static 28px pill, requiring the user to manually click any pill to inspect its status or contents.
*   **Pros**:
    *   Enforces an ultra-compact visual rhythm with zero exceptions.
    *   Simpler UI state management without automated expansion triggers.
*   **Cons**:
    *   Silently hides critical upstream failure modes: an agent stuck in a schema loop or blocked by an AST safety guardrail appears as normal green pills unless manually clicked.
    *   Slows down failure diagnosis by requiring manual probing of every non-query turn.
*   **Reason for Rejection**: *Rejected by author: Unconditionally collapsing non-query events conceals critical upstream schema loops and security policy rejections.*

### Alternative 4: Full-Screen Modal Inspector for Database Rows

*   **Description**: Render SQL cards with query text only, opening a full-screen modal or drawer to view returned rows and columns.
*   **Pros**:
    *   Allows displaying very wide tables (20+ columns) without horizontal scroll constraints within the card.
*   **Cons**:
    *   Breaks chronological reading flow by covering the trace timeline.
    *   Completely inhibits side-by-side visual comparison of Baseline versus Candidate query results in the dual-arm tournament view (`apps/web/src/comparison.tsx`).
*   **Reason for Rejection**: *Rejected by author: Modal overlays break chronological flow and prevent side-by-side visual comparison across tournament arms.*

## Non-Functional Requirements

### 1. Security & Privacy
*   **Read-Only Integrity**: The workbench is purely a presentation layer. It does not introduce any interactive input fields capable of executing ad-hoc SQL or modifying database state.
*   **Redaction Preservation**: All strings rendered in the SQL block and reasoning drawer are sourced from canonical `TraceEvent` payloads that have already undergone server-side redaction (per HarnessLab trust boundaries). No raw credentials or unredacted provider tokens are exposed.

### 2. Performance & Latency
*   **DOM Node Footprint**: Task runs can contain 50+ trace events. By constraining tabular result viewports to `max-height: 260px` and capping initial table row renders to 100 rows with overflow indicators, the workbench prevents layout recalculation lag.
*   **Pure Stream Parsing**: `clusterTraceEvents` runs synchronously in memory with $O(N)$ linear complexity, adding negligible overhead (<2ms) on a 100-event trace.

### 3. Rollout & Backward Compatibility
*   **Zero Impact on Business View**: The workbench is strictly scoped to `viewMode === "technical"`. When `viewMode === "business"`, the existing executive scorecard and `LiveDataView` presentation remain 100% untouched.
*   **Graceful Degradation**: If a trace contains malformed payloads or zero SQL queries, the workbench falls back to displaying clear empty-state banners without crashing the React tree.

#### 2. `apps/web/src/workbench/parser.ts` (Create)
*   **Type / Scope**: Pure Utility Module (Event Stream Clusterer)
*   **Proposed Changes**:
    *   Export pure function `clusterTraceEvents(items: TraceEvent[]): ExecutionStep[]`.
    *   Track preceding `model_usage` payload to extract agent reasoning text.
    *   Pair `execute_readonly_sql` requests with their matching `tool_result` into `SqlQueryStep`.
    *   Map non-SQL events (`describe_schema`, `list_tables`, `validate_calculation`, `policy_decision`, `start`) into `NonQueryLogStep`.
    *   Compute `autoElevate: true` whenever:
        *   `event.outcome_code && event.outcome_code !== "success"`
        *   `item.kind === "policy_decision" && item.payload.decision !== "allow"`
        *   `item.kind === "tool_result" && item.payload.status !== "ok"`
